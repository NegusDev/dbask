# Security Policy

## Supported Versions

Security fixes are applied to the latest maintained version of DBAsk.

Users are encouraged to keep their installations updated to the latest published release.

| Version | Security Updates |
|---|---|
| Latest release | Supported |
| Older releases | Not guaranteed |

## Reporting a Vulnerability

If you discover a security vulnerability in DBAsk, please report it responsibly.

**Do not disclose security vulnerabilities through public GitHub issues or public discussions.**

Use GitHub's private vulnerability reporting feature:

[Report a vulnerability](https://github.com/NegusDev/dbask/security/advisories/new)

When submitting a report, include:

- A description of the vulnerability.
- Steps to reproduce the issue.
- The affected DBAsk version.
- Potential security impact.
- Relevant logs, screenshots, or proof-of-concept code, where appropriate.

Please avoid including actual database credentials, API keys, personal information, or production data in your report.

We will review submitted reports and work towards a fix. Please allow time for investigation before publicly disclosing a vulnerability.

## Security Considerations

DBAsk connects AI models to existing databases and executes SQL generated during agent interactions. Its security depends on both the safeguards implemented by DBAsk and the configuration of the environment in which it runs.

### 1. Database Access

DBAsk should be configured with a dedicated database account that has only the permissions required for its intended operations.

For read-only use cases:

- Use a database account with `SELECT` permissions only.
- Avoid using database administrator or root accounts.
- Restrict access to unnecessary databases and tables.
- Apply database-level permissions appropriate to your application.
- Use encrypted database connections where supported and required by your environment.

DBAsk includes SQL validation and read-only query restrictions. However, these safeguards should not replace database-level access controls.

### 2. SQL Execution

DBAsk provides SQL safety checks intended to restrict query execution to permitted read operations.

Users should be aware that:

- SQL generated by an AI model may be incorrect or incomplete.
- A syntactically valid query is not necessarily semantically correct.
- SQL validation does not guarantee that a query is appropriate for every application.
- Query limits and execution timeouts should be configured according to the deployment environment.
- Important results should be independently validated.

Never rely exclusively on AI-generated SQL for critical business, financial, or operational decisions.

### 3. Database Credentials and API Keys

Database credentials and AI provider API keys must be treated as sensitive information.

- Store credentials in environment variables or an appropriate secrets manager.
- Do not commit `.env` files or credentials to version control.
- Do not expose server-side environment variables through frontend applications.
- Do not include credentials in logs, error responses, or support requests.
- Rotate credentials immediately if they are suspected to have been exposed.

DBAsk does not require users to share their provider API keys with the DBAsk project maintainers. Users configure their own AI provider credentials.

### 4. AI Provider Data Exposure

DBAsk uses external AI providers to process requests.

Depending on the configured provider and integration, database schema information, user questions, generated SQL, and query results may be sent to that provider as part of an interaction.

Users are responsible for:

- Reviewing their AI provider's privacy and data retention policies.
- Understanding how submitted data may be processed or retained.
- Avoiding unnecessary transmission of sensitive information.
- Selecting providers and configurations appropriate for their data protection requirements.

Do not assume that database information remains entirely within your infrastructure when using an external AI provider.

### 5. Application and Multi-Tenant Security

When integrating DBAsk into an application, developers are responsible for implementing application-level authentication and authorization.

In particular:

- Authenticate users before allowing database interactions.
- Enforce permissions independently of AI-generated instructions.
- Restrict access to records belonging to the authenticated user or organization.
- Do not rely on prompts alone to enforce authorization.
- Apply rate limits to prevent abuse and excessive resource consumption.
